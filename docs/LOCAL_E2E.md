# Local end-to-end tests: the Kit against the real web backend

The Kit's unit tests replay response bodies that were copied from a deployment. They cannot tell you whether the
app still agrees with the server that is deployed today, and the routes that need a signed-in person had never
been run against any server at all. These tests do that: they bring up the **real web app** (the `hypervault-web`
checkout, unmodified) over a **real PostgreSQL** with the repo's **real migrations**, sign people in with throwaway
tokens, and drive the Kit's `Endpoint`s and models through realistic journeys for every feature area.

Nothing leaves the machine. No request goes anywhere but `127.0.0.1`, no real credential is read, every key,
token and user is generated by the start script. It does not touch the production Supabase project or any
deployment.

## Run it

```sh
# 1. Bring everything up (about 2.5 minutes from nothing, see "How long it takes").
HYPERVAULT_WEB=/path/to/hypervault-web scripts/e2e/start.sh

# 2. Run the Kit's end-to-end tests with the variables the script wrote.
. /tmp/hv-e2e/env.sh
cd Packages/HyperVaultKit
swift test --filter 'LocalServerE2ETests|LocalE2E'

# 3. Stop everything (data stays in /tmp/hv-e2e; add --purge to delete it).
scripts/e2e/stop.sh
```

Options of `start.sh`:

| Option | Meaning |
| --- | --- |
| `--reset` | stop, delete `$HV_E2E_DIR`, and start from an empty cluster |
| `--no-web` | the Supabase stand-in only (to run the web app yourself) |
| `--build` | `next build` + `next start` instead of `next dev` (slower to start, faster to run; less exercised) |
| `--no-warm` | skip compiling every route before the tests (`next dev` compiles a route on first use) |

Settings (environment): `HYPERVAULT_WEB` (required), `HV_E2E_DIR` (default `/tmp/hv-e2e`), `HV_E2E_PG_PORT`
(54329), `HV_E2E_STACK_PORT` (54321), `HV_E2E_WEB_PORT` (3100), `HV_E2E_FAKES_PORT` (54340),
`HV_E2E_POOL_USERS` (how many pool members the seed creates, default 32), `HV_E2E_STRICT_URLS=1` (see below),
`PG_BIN`, `NODE`.

The tests skip, so the normal `swift test` (and CI) is unaffected, unless both of these are set:

| Variable | What |
| --- | --- |
| `HV_E2E_LOCAL_SERVER` | the web app, `http://127.0.0.1:3100` |
| `HV_E2E_LOCAL_TOKEN` | a signed-in member's access token |

Optional, and the tests that need them skip when they are missing: `HV_E2E_LOCAL_TOKEN_2` (a second member:
sharing, isolation), `HV_E2E_LOCAL_ADMIN_TOKEN` (an administrator), `HV_E2E_LOCAL_WAITLIST_TOKEN` (signed in but
not let in: invite redeem), `HV_E2E_LOCAL_EXPIRED_TOKEN`, `HV_E2E_LOCAL_POOL_TOKENS` (comma separated members, one
per feature area, so no one person runs into the server's 120-calls-a-minute meter), `HV_E2E_SUPABASE_URL`,
`HV_E2E_ANON_KEY`, `HV_E2E_SERVICE_KEY` (the stand-in, for the Kit's direct reads and for arranging rows the Kit
has no call to create), `HV_E2E_FAKES` (the model / MCP / webhook stand-ins). Debug aids: `HV_E2E_TRACE=1` prints
every request with its status and time, `HV_E2E_KEYS=1` prints the JSON key names the server sent for every call
(to set against the names the Kit reads).

The tokens last 24 hours. After that, run `start.sh` again (it re-seeds and rewrites `env.sh`).

## What you need

Everything is on the machine already; the scripts install and download nothing.

- **The web repo**, at a commit that accepts `Authorization: Bearer <supabase jwt>` on session-only routes
  (`hypervault#180`, branch `claude/bearer-aware-session`), with its `node_modules` already installed.
  The scripts never modify it; they configure it with environment variables.
- **PostgreSQL server and client binaries** (`initdb`, `pg_ctl`, `psql`; found under `/usr/lib/postgresql/*/bin`;
  16 is what it was built and run with).
  Run as root, the cluster is owned by the `postgres` account.
- **Node 20+** (`/opt/node22/bin/node` is preferred). The stand-in has no dependencies.
- **Swift 6** for the Kit tests.

## How long it takes

Measured on the machine this was built on (a container, `next dev`, the web repo's `.next` cache already there, so a
first-ever run compiles more): from nothing, `start.sh --reset` has the cluster, 64 migrations, the stand-in and the
seeded people ready in about 2 seconds and the web app answering `/api/capabilities` at about 8 seconds. Compiling the
150 routes ahead of the tests takes another 145 seconds (`--no-warm` skips it; the first test to touch each route
then waits for its compile). Ready in about 2 minutes 40 seconds in all. The suite then runs in about 5 minutes,
much of it the Kit pacing its own calls (see below) and the two tests that run a meter dry.

## What stands up

`scripts/e2e/` is plain Node, no packages.

- **`stack.mjs`** is the Supabase stand-in, one HTTP server:
  - `/auth/v1`, a fake GoTrue (`lib/gotrue.mjs`): HS256 JWTs, email codes (the code is always `424242`),
    refresh tokens that are single use, `GET /user` (which is how the web app validates a bearer token).
  - `/rest/v1`, a PostgREST-compatible layer (`lib/postgrest.mjs`) built from the documented behaviour: resource
    embedding, `select`/filters/`order`/`limit`/`offset`, `Prefer` (`return=representation`, `resolution=`,
    `count=`), upsert with `on_conflict`, `rpc` functions, the error mapping (`23505` is 409 and so on). **Row-level
    security is real**: each request runs in a transaction with `SET LOCAL ROLE` and `request.jwt.claims`, so the
    policies and column grants in the migrations decide what a person can read.
  - `/storage/v1`, enough object storage for signed uploads and downloads (`lib/storage.mjs`).
- **PostgreSQL** with `sql/bootstrap.sql` (the `auth` schema, the `anon`/`authenticated`/`service_role` roles, the
  few Supabase functions the migrations lean on) and **every migration in the web repo**, applied in order by
  `apply-migrations.mjs` after `transform-migration.mjs` rewrites what plain PostgreSQL does not have:
  `vector(N)` becomes `real[]`, `create extension vector` goes, ivfflat/hnsw indexes are dropped, and the `<=>`
  operator is defined in SQL (so recall works, without an index and without the real pgvector maths).
- **`seed.mjs`** creates the people and mints their tokens: `alice` (the main member), `bob`, `admin`
  (`admin@e2e.test`, an administrator by `HYPERVAULT_ADMIN_EMAILS`), `carol` (waitlisted) and 32 pool members.
- **`fakes.mjs`** stands in for the outside services the web app calls, so those routes can be exercised without
  any: an OpenAI- and Anthropic-compatible model that echoes (with embeddings), an MCP server over Streamable HTTP
  (with a `Bearer` variant that answers 401 with a challenge), and a webhook receiver that records what it was sent.
  The web app only calls a private address when told to (`HYPERVAULT_ALLOW_LOCAL_LLM=1`, `HYPERVAULT_ALLOW_LOCAL_MCP=1`),
  which `start.sh` sets. Set **`HV_E2E_STRICT_URLS=1`** to leave that off: the tests that need the stand-ins skip,
  and the ones that check the server refuses `127.0.0.1`, `169.254.169.254`, `localhost` and `10.0.0.1` as webhook
  or MCP addresses assert the refusals instead.
- **The web app** (`next dev` by default) on port 3100 with the stand-in as its Supabase project and these
  switches on: `HYPERVAULT_KEY_SECRET` (so model keys can be stored), `HYPERVAULT_PAIRING`,
  `HYPERVAULT_SHARE_ROLES`, `HYPERVAULT_GUEST_KEEP`, `CRON_SECRET`. It starts with no mail provider, GitHub,
  Anthropic or embeddings keys, on purpose.

The server meters each signed-in person at 120 calls a minute and each agent key at 60 (in memory, per process).
A suite this long would run into it, so the tests send through a transport that spaces every person's calls to
under 100 in any 60 seconds, and give each feature area its own member from the pool (`LocalE2ECase.member(n)`).
The tests that want the meter (`LocalE2EStatusTests`) bypass the pacing and use a person made for the purpose
(`freshMember`, signed up through the Kit's own `AuthService` and let in by the administrator).

## What the tests check

Each test compares what a model decoded with the raw JSON the server sent, or writes something and reads it back
by another route; "it decoded" proves little when most models fall back to empty values. Every call also checks
that each timestamp the server sent is one the Kit's `HVDate` can read.

| Area | Tests (class) | Covers |
| --- | --- | --- |
| Sign-in state, capabilities, keep, Yours | `LocalServerE2ETests` | anonymous and signed-in capabilities, 401 for no/bad/expired tokens, 403 waitlist, 404, keep (notes, HTML, React, duplicates), the Yours filters |
| Session-only routes | `LocalE2ESessionRoutesTests` | agent keys (mint, list through the Kit's own PostgREST read, scopes, the setup challenge page's slug, revoke), the artifact source route, onboarding flags, invite redeem, admin (probe, accounts, plans), the Kit's own sign-in (email code, refresh, sign-out, refresh on 401) |
| Pages | `LocalE2EArtifactsTests` | save, versions, diff, revert, rebase, 428/409 conflicts, immutable pages, visibility, sharing roles, leaving a share, passwords, feedback, icons, connections, pins, deleting, groups and their files |
| Memory and Mind | `LocalE2EMemoryTests` | memorize, search, edit, forget, bring back, file import, links and graph, size limit, branches, commits, compare, time travel, merge (clean and conflicting) and revert |
| Account | `LocalE2EAccountTests` | the Kit's vault rules against the server's (accepted and refused alike), keys, webhooks, claimed addresses, dreams, digest, background jobs |
| Mail | `LocalE2EMailTests` | provisioning, summaries, notes to agents, the send scope, held mail, replies, export, isolation between people |
| Truth | `LocalE2ETruthTests` | ledgers, handles, assertions, contests, the docket, supersede and ripple, hosted ledger streams and mirrors, page imports and proposals, signers, rooms |
| Task boards | `LocalE2ETaskBoardTests` | create and read three ways, every edit the app makes against the Kit's prediction, stale writes, agent claims |
| Chat and rooms | `LocalE2EChatTests` | connecting a model (key stored encrypted, never returned), a turn grounded in recalled memories, on-device turns, settings, rooms with two agents |
| Tools | `LocalE2EToolsTests` | MCP servers (preview, add, edit, refresh, compile, sign-in challenge, refused addresses), signed webhook deliveries |
| Imports | `LocalE2EImportTests` | ChatGPT, Claude, Grok and pasted histories, an export inside a zip, batching, halving an overlarge batch |
| The rest | `LocalE2EMoreTests` | image and PDF upload and serving, the canvas and Ask turns, asking a room about a truth item, the connect documents, the admin waitlist, routes whose service is not here |
| Refusals | `LocalE2EStatusTests` | 412 on a strict `If-Match`, 413 on save/keep/write (and 1,000,000 bytes accepted), 429 from the person meter (120) and the key meter (60), the Kit's retry of reads but not writes |

401, 403, 404, 409, 412, 413, 428 and 429 are all reached by a real route.

## What is not covered

- **A real model, embeddings service or MCP registry.** Model turns go to the echo stand-in, so the tests prove the
  route, the saving, the grounding in recalled memories and the error mapping, not the quality of an answer.
  Searching the MCP registry and the stenographer sidecar need services that are not here; those routes are
  asked and their plain answers recorded.
- **Mail delivery, payments, GitHub, push notifications.** No provider is configured. Mail is exercised through the
  database (the tests arrange inbound messages as the service role), not through a provider.
- **pgvector.** Recall runs on `real[]` with a plain `<=>`, with no approximate index, so ranking is right in shape
  but the index and the real distance operator are not exercised.
- **PostgREST itself.** The layer is written from the documented behaviour. A difference between it and the real
  thing would show as a failure here that production does not have (or hide one it does). The Kit's direct reads
  (`AccountRest`, `ArtifactTables`, `InviteRedeemer`) are the calls most exposed to that.
- **GoTrue itself.** OAuth, magic links, Apple sign-in and password flows are not stood in; the email-code flow
  and token refresh are.
- **`next build` mode** is supported by `--build` but the suite was run against `next dev`. Rate-limit recovery
  after the minute is not waited out.
- **The app.** SwiftUI is not compiled on Linux. The app-level fixes found here are covered by tests in
  `Tests/AppTests`, which run in CI on macOS.
- **Other servers.** The tests are written against the web repo at the commit named above; a deployment with a
  different build can disagree in ways this does not see. `LiveAuthenticatedTests` (with `HV_E2E_SERVER` and `HV_E2E_KEY`)
  is the opt-in read-only check against a deployment with your own key.

## When something fails

- Everything fails with 401: the tokens are older than 24 hours, or `env.sh` is from another data directory. Run
  `start.sh` again.
- Connection refused: the web app is still compiling a first route (`tail -f /tmp/hv-e2e/logs/web.log`), or the
  stand-in died (`logs/stack.log`).
- A test that passes alone and fails in the suite is almost always a person's meter or state that piles up on an
  account; give it its own member or `freshMember`.
- Postgres says permission denied for its log: the cluster is created for the `postgres` account; run `stop.sh --purge`
  and start again.
